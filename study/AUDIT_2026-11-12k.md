## 2. Claim A, the pointer (question 2)

**What the pointer is** (`token_sources`, `oracle_pointer` at `f2cb45be1`):
- The source is the prompt's last line only: the instruction and the sentence to edit.
- Each token of gold + closing (the host tokenizer's tokens) is matched by bytes in that line, from a cursor that moves through the sentence. A token not found after the cursor takes its first occurrence in the line, which is where an inserted or substituted word sits, in the instruction.
- At a deciding row the piece about to be written is taken from the gold. The pointed row is the prompt token that holds that piece's last byte, and `assert p <= r`.
- The pointed row is always a row of the prompt's last line: `last = start + s0 + len(piece) − 1`, with `s0` an offset into the line. It is never a row of the answer so far or of the gold.
- In `count` the host's input is prompt + gold[:-1] (teacher forcing), and the pointer still lands only on prompt rows. Under teacher forcing, "written so far" is always a gold prefix, so the pointer is set wherever the next token has a source.

**What it gives the host.** `WeightsSwap` replaces the 15 heads' outputs at the set rows by the pointed row's value vector in each head: one-hot weights over the host's own values. Nothing else enters.

But on these four tasks the token at the pointed row is the next gold token, by construction. So the position is the answer, written as an index into the prompt:
- 15 heads at once write that token's value vectors into the residual stream at every deciding row;
- what the host then contributes is its heads' value-to-output map and the formatting (the closing is also pointed at, to the prompt's quote).

That is "heads copy from where they are pointed". It does not show how much of the task the host holds beyond copying. The rows show the limit of even that:
- with the pointer set, Pythia still writes the word the edit removes on some items, such as `del_word:0039` (` from`), `del_word:0064` (` loud`) and `sub_word:0080` (` do`);
- the pointed heads lose to the rest of the host on 14 of 90 items.

**Is the comparison with F's weights fair?**

| point | finding |
|---|---|
| Host heads | The same 15 (and 27) host heads in both specs (checked from the request). |
| Pointer pairs | `[hl, hh, 0, 0]` with `"donor": "oracle"`. |
| List and counting | The same select list, in the same `count` pass. |
| Rows | The same deciding rows: both come from `vectors`, which still parses the text with F and S to keep the host rows whose span matches an F and an S patch. |

So the pointer runs with the donor's parse, and "no donor" is not literal: the donor's weights are unused, but its parse sets the rows.

One asymmetry: the pointer writes only the rows where it has a source and leaves the others to the head's own output, while F's weights overwrite every deciding row. On these tasks almost every row has a source.

**The swap defect.** I re-ran `token_sources`' byte rule on the actual select list, with word-level pieces in place of Pythia's tokens:
- a piece lands inside a longer word on 5 of 30 swap items and on 0 of 90 delete, insert and substitute items;
- the defect can only make the pointer wrong, which lowers the pointer's count;
- so 76 of 90 is unaffected, and swap's 17 of 30 is a lower bound for a correct pointer.

**Which number is the read.** The rule written before launch (21:31:05Z by git) reads delete, insert and substitute only. The read is therefore 76 against 43 of 90. GRAFT (0), the journal's title, HANDOFF and SCOREBOARD lead with 93 of 120, which includes the swap items the rule said not to read.
